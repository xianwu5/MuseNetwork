## 一、SIM-003｜WAN B 光链路质量异常

### 1. 客户问题

某贸易公司反馈：

- ERP偶发等待3～6秒
- 海外SaaS网页偶尔转圈
- 普通网页基本正常
- Ping和测速看起来正常
- 故障主要出现在WAN B路径

网络采用双WAN架构：

- WAN A：普通办公出口
- WAN B：部分海外业务出口

### 2. 初步排查

| 检查项目 | 结果 | 判断 |
| --- | --- | --- |
| NAT | 会话资源充足 | 嫌疑下降 |
| ERP服务器 | CPU、内存正常 | 暂无性能瓶颈证据 |
| DNS | 解析正常 | 嫌疑下降 |
| 路由策略 | 部分业务走WAN B | 需要继续验证 |
| WAN A对照测试 | 业务稳定 | 形成对照 |
| WAN B对照测试 | 偶发2～5秒停顿 | 故障集中在WAN B |

关键发现：

- TCP HTTPS出现Retransmission
- 偶发Dup ACK
- 大报文比小报文更容易丢失
- WAN A同类业务基本正常

### 3. 物理层排查

WAN B接口数据：

- Speed：1000M Full
- CRC：15分钟内从328增长到517
- RX光功率：接近接收下限
- TX光功率：正常
- 接口没有频繁Up/Down

初步结论：WAN B接收方向存在物理链路质量异常。

注意：不能直接认定本端光模块损坏。

### 4. 逐步验证

按照低风险到高风险顺序处理：

1. 检查接口计数器、光功率和告警。
2. 检查跳纤弯折、接头污染和松动。
3. 更换已知正常的本端跳纤。
4. 观察RX和CRC变化。
5. 在维护窗口更换已知正常的同规格本端光模块。
6. 继续检查对端TX、对端接口状态和中间光路。
7. 使用专业光功率测试或链路测试工具定位衰耗。

模拟现场结果：

- 更换本端跳纤后，RX仅改善约0.3dB。
- 更换本端光模块后，RX仍然偏低。
- 对端TX正常。
- 中间光路衰耗比设计值高约4dB。
- 最终发现中间熔接点损耗异常。

处理后：

- 本端RX恢复正常范围。
- CRC不再持续增长。
- TCP重传明显下降。
- 海外SaaS连续测试30分钟未再出现明显停顿。

### 5. Root Cause

WAN B中间光路熔接点异常，造成额外光衰耗，导致本端接收光功率偏低，出现CRC错误和报文丢失，最终引发TCP重传及业务卡顿。

### 6. 整改与验收

整改：

- 修复异常熔接点。
- 复测光功率。
- 检查接口错误计数器。
- 对比TCP重传。
- 分别通过WAN A、WAN B测试业务。

验收：

- RX/TX处于模块正常工作范围。
- CRC不再持续增长。
- 接口无异常告警。
- TCP重传明显改善。
- 业务连续性测试通过。

### 7. 本案例知识点

- Interface Up不代表物理链路质量正常。
- Ping正常不代表TCP传输没有问题。
- CRC持续增长说明接收帧校验异常，但不能直接定位故障器件。
- RX低需要沿着完整接收光路追踪。
- 本端光模块、跳纤、对端TX、中间光路都可能造成光功率异常。

关键口诀：先定位故障层，再定位故障件。

## 二、SIM-004｜单千兆上联拥塞导致业务卡顿

### 1. 客户环境

某企业办公网络：

- 20台办公PC
- 6台网络摄像头
- 2台无线AP
- 1台NAS

网络拓扑：

办公PC / CCTV / AP / NAS
↓
接入交换机
↓
1×1Gbps上联
↓
汇聚交换机

### 2. 客户问题

- 上午网络正常。
- 下午文件传输速度下降。
- 视频会议偶发卡顿。
- 公网测速不稳定。
- 交换机接口保持Up。
- 没有明显CRC/Error。

### 3. 第一轮排查

| 检查项目 | 数据 | 判断 |
| --- | --- | --- |
| CPU | 22% | 正常 |
| 内存 | 47% | 正常 |
| 上联速率 | 1000M Full | 正常协商 |
| CRC/Error | 基本为0 | 暂无物理层异常 |
| VLAN | 未发现异常广播/组播 | 嫌疑下降 |
| ERP服务器 | CPU约31% | 暂无明显性能瓶颈 |

### 4. 上联流量分析

下午15:20～15:40：

| 项目 | 流量 |
| --- | --- |
| 上联出方向 | 780～930Mbps |
| 出方向峰值 | 960Mbps以上 |
| 上联入方向 | 210～320Mbps |
| NAS大文件传输 | 420～500Mbps |
| CCTV | 约120Mbps |
| AP汇聚流量 | 180～250Mbps |
| 普通办公及其他 | 约100Mbps |

上联出方向已经接近千兆链路容量。

但要注意：利用率高只是拥塞嫌疑，还需要证明实际发生了丢包。

### 5. 关键证据：Output Drop和队列

Output Drop：

| 时间 | 计数 |
| --- | --- |
| 15:20 | 12,480 |
| 15:30 | 18,960 |
| 15:40 | 26,300 |

队列状态：

- 普通业务队列长期处于高水位。
- 多次出现瞬时队列打满。
- 视频会议和普通数据共用同类队列。

证据链：业务并发 → 单千兆上联接近饱和 → 出方向队列堆积 → Queue Drop / Output Drop → TCP重传及实时业务等待 → 用户感知卡顿。

### 6. Root Cause

接入交换机到汇聚交换机之间采用单条1Gbps上联，高峰期多类业务并发导致出方向拥塞，产生队列丢弃，最终影响文件传输和视频会议。

### 7. 整改方案

方案A：QoS业务分类

| 业务 | 优先级 | 处理方式 |
| --- | --- | --- |
| 视频会议/语音 | 最高 | 保障低延迟、低抖动 |
| ERP/办公 | 高 | 保证核心办公体验 |
| CCTV | 保障型 | 保证持续录像所需带宽 |
| NAS大文件 | 较低 | 限速、错峰传输 |

注意：CCTV不能简单设置为最低优先级，必须保障录像完整性。

方案B：NAS限速与错峰

白天：

- 初始限速200～250Mbps。
- 根据实际业务调整。
- 不影响必要的文件访问。

晚上：

- 提高或解除限速。
- 完成批量备份和同步。

CCTV：

- 如果系统支持本地录像缓存，白天优先本地存储。
- 夜间进行云端同步。

方案C：2×1G Eth-Trunk

在两端设备均支持、接口和配置条件满足的情况下：1×1G升级为2×1G Eth-Trunk。

优势：

- 增加多流并发总体容量。
- 提供成员链路冗余。
- 降低单条千兆链路的压力。

注意：2×1G不代表单个TCP流一定能获得2Gbps。链路聚合通过哈希分配流量，单个流通常仍由一个成员链路承载。

方案D：长期升级10G

如果业务持续增长，规划10G上联。

需要检查：

- 两端设备10GE能力。
- 光模块规格。
- 光纤类型。
- 传输距离。
- 接口兼容性。
- 布线条件。

### 8. 验收标准

| 验收项目 | 验收要求 |
| --- | --- |
| 上联利用率 | 不再长期接近容量上限 |
| Output Drop | 停止增长或明显下降 |
| Queue Drop | 明显改善 |
| 视频会议 | 高峰期稳定 |
| ERP | 操作响应正常 |
| NAS | 白天满足业务，夜间完成备份 |
| CCTV | 在线正常、录像完整 |
| Eth-Trunk | 成员链路正常，单成员故障测试通过 |

注意：以上是验收目标，不是已经实施后的实测结果。真实项目必须补充整改后数据。

### 9. 本案例知识点

- 接口Up不等于链路没有拥塞。
- CRC为0不代表没有队列丢包。
- 利用率高不等于已经证明业务受损。
- Output Drop和队列数据可以证明拥塞是否真正影响转发。
- QoS解决业务争抢，扩容解决总体容量不足。
- Eth-Trunk不能简单等同于单流带宽翻倍。

关键口诀：接口忙不等于拥塞，队列丢包才是关键证据之一。

## 三、SIM-005｜IPsec VPN下MTU/MSS异常

### 1. 客户环境

某企业约60人办公网络：

- 企业出口路由器
- 防火墙
- IPsec VPN
- 云端业务系统
- 普通Internet访问

### 2. 客户问题

- 普通网页访问正常。
- VPN对端Ping正常。
- TCP 443可以建立。
- 小文件传输正常。
- 大附件上传失败或卡住。
- 复杂页面偶发超时。
- 问题只发生在经过VPN的业务。

### 3. 第一轮排查

| 检查项目 | 结果 | 判断 |
| --- | --- | --- |
| MTU | 普通接口1500 | 需要检查路径MTU |
| TCP重传 | 大数据段出现重传 | 强烈嫌疑 |
| 安全策略 | TCP443已放行 | 嫌疑下降 |
| IPsec SA | 正常建立，计数增长 | 隧道已建立 |
| MSS调整 | 未配置针对性调整 | 需要进一步验证 |

### 4. 故障原理

普通以太网常见MTU为1500字节。

IPsec封装会增加额外头部开销。

原始报文经过VPN封装后，可能超过路径能够承载的最大报文尺寸。

如果中间设备不能正确处理分片，或者相关ICMP报文被过滤，就可能出现PMTUD Black Hole。

典型现象：

- 小包正常。
- TCP三次握手正常。
- 小文件正常。
- 大文件或复杂页面异常。
- TCP持续重传。

### 5. Windows测试Path MTU

命令：

```
ping 10.20.30.40 -f -l 1472
```

参数：

- -f：设置DF，不允许分片。
- -l：设置ICMP数据负载大小。

IPv4基础计算：IPv4头20字节 + ICMP头8字节。

因此：Path MTU = ICMP Payload + 28。

### 6. 本次实操数据

| ICMP Payload | 测试结果 |
| --- | --- |
| 1472 | 失败 |
| 1400 | 成功 |
| 1440 | 失败 |
| 1420 | 成功 |
| 1430 | 失败 |
| 1424 | 成功 |
| 1426 | 成功 |
| 1427 | 失败 |

最大成功ICMP Payload为1426。

因此：Path MTU = 1426 + 28 = 1454字节。

IPv4基础TCP MSS估算：MSS = 1454 - 20 - 20 = 1414字节。

最终答案：

- Path MTU：1454字节。
- 基础TCP MSS：1414字节。

### 7. 整改思路

确认问题后：

1. 检查VPN两端MTU。
2. 检查IPsec封装开销。
3. 检查DF和分片处理。
4. 检查相关ICMP报文是否被过滤。
5. 根据实测Path MTU调整TCP MSS。
6. 通过抓包确认TCP数据段尺寸和重传变化。
7. 重新测试大文件上传和复杂页面访问。

MSS调整不能直接照抄1414，最终数值需要结合实际封装、设备行为、TCP协商和抓包验证。

### 8. 验收

- VPN路径大报文测试通过。
- TCP重传明显下降。
- 大附件上传成功。
- 复杂页面正常加载。
- 普通Internet业务没有受到负面影响。
- VPN连接稳定。

### 9. 本案例知识点

- MTU是IP层报文尺寸限制。
- MSS是TCP层最大数据段尺寸。
- IPsec封装会增加额外开销。
- Ping通不代表大报文可以正常传输。
- TCP握手成功不代表后续数据传输正常。
- PMTUD依赖路径正确反馈报文过大的信息。

关键口诀：小包正常、大包异常，优先考虑Path MTU；握手正常、数据卡顿，检查MSS和PMTUD。

## 五、当前最需要补强的技术能力

### 1. 物理层

需要继续学习：

- 光模块DOM信息。
- RX/TX光功率。
- 光功率预算。
- CRC、Input Error、Output Error。
- 光纤衰耗。
- 跳纤和熔接点。
- LOS与接口Flap。

### 2. 交换机转发与拥塞

需要继续学习：

- 接口利用率计算。
- Queue Drop。
- Output Drop。
- 微突发。
- QoS队列调度。
- Eth-Trunk/LACP。
- 哈希负载分担。

### 3. IP层与TCP

需要继续学习：

- MTU与MSS。
- Path MTU Discovery。
- DF测试。
- TCP Retransmission。
- Dup ACK。
- TCP窗口。
- 分片与PMTUD Black Hole。

### 4. 工程判断

当前尤其要强化：

- 不能从一个异常数据直接认定具体故障件。
- 不能把接口Up当作链路正常。
- 不能把测速正常当作业务正常。
- 不能把带宽利用率高直接等同于丢包。
- 不能把Ping通当作应用正常。
- 整改前必须考虑风险、回退和维护窗口。

## 六、企业网络排障 SOP 候选 V0.3

### 第一步：故障现象确认

记录：

- 发生时间。
- 影响范围。
- 影响业务。
- 有线还是无线。
- 是否所有用户都受影响。
- 是否具有周期性。

### 第二步：建立基线

检查：

- Ping网关。
- Ping目标地址。
- TCP端口。
- DNS解析。
- 带宽利用率。
- CPU/内存。
- 接口状态。

### 第三步：按故障域排查

物理层：

- 光功率。
- CRC/Error。
- 光模块。
- 光纤。
- 接口协商。

二层：

- VLAN。
- STP。
- 广播/组播。
- 上联拥塞。
- Queue Drop。

三层：

- 路由。
- PBR。
- NAT。
- MTU。
- 路径质量。

传输层：

- TCP重传。
- Dup ACK。
- MSS。
- 会话状态。

应用层：

- DNS。
- TLS。
- 认证。
- 服务器CPU/内存。
- 数据库性能。
- 应用日志。

### 第四步：形成证据链

每次排障必须记录：

1. 现象是什么？
2. 哪些数据支持当前判断？
3. 还有哪些可能原因？
4. 用什么方法排除？
5. 最终根因是什么？

### 第五步：整改

必须包含：

- 变更内容。
- 变更前备份。
- 影响范围。
- 操作步骤。
- 回退方案。
- 维护窗口。

### 第六步：验收

至少进行：

- 故障场景复测。
- 业务功能测试。
- 设备状态检查。
- 关键计数器对比。
- 稳定性观察。
- 客户确认。
