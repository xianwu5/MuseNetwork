# 知识点：TCP 快速重传、快速恢复与拥塞控制

日期：2026-11-08
所属月份/阶段：第 1 个月 / 补短板（TCP）

## 核心概念

一句话：超时重传是等，没等到才补发；快速重传是不等，收到 3 个重复 ACK 就认定丢了，立刻补发。

### 快速重传（Fast Retransmit）

- 触发条件：发送方收到 3 个重复 ACK（也就是第 4 个对同一序列号的 ACK）。
- 为什么是 3 个：网络里偶尔会有 1-2 个包乱序，收到 1-2 个重复 ACK 不一定是丢包。连收 3 个，基本可以断定中间那个段丢了。
- 动作：不等 RTO 超时，立即重传疑似丢失的那个段。
- 测评原题的点：收到 3 个重复 ACK 时立即重传并进入快速恢复，而不是等超时。

### 快速恢复（Fast Recovery，Reno）

- 收到 3 个重复 ACK 后，说明网络还在通（对端还在回 ACK），只是丢了一个段，拥塞不算严重，不用回到慢启动。
- 做法：ssthresh = 当前 cwnd / 2，cwnd = ssthresh + 3 个 MSS（3 是已经收到的 3 个重复 ACK 对应的已离队数据）。
- 之后每再收到一个重复 ACK，cwnd + 1 个 MSS；收到新数据的 ACK 时，cwnd = ssthresh，进入拥塞避免。
- 对比 Tahoe：Tahoe 没有快速恢复，快速重传后 cwnd 直接回到 1 个 MSS，重新慢启动，更保守、恢复更慢。

### 拥塞控制全图

- 慢启动：cwnd 从 1 个 MSS（现代实现常用 10）开始，每个 RTT 翻倍，直到达到 ssthresh。
- 拥塞避免：超过 ssthresh 后，cwnd 每个 RTT 只加 1 个 MSS，线性增长。
- 超时丢包：ssthresh = cwnd / 2，cwnd = 1，回到慢启动。这是最重的惩罚，说明网络真的堵了。
- 重复 ACK 丢包：快速重传 + 快速恢复，cwnd 减半但不归 1，说明只是轻微丢包。
- 这就是 AIMD：加性增、乘性减。平时慢慢加，出事一次减半。

## 关键结论 / 容易记混的点

- 3 个重复 ACK = 触发快速重传，不是 3 次超时，也不是 3 个包丢了。
- 快速重传省的是等待 RTO 的时间，RTO 通常是几百毫秒到几秒，快速重传是 RTT 级别。
- 快速恢复和慢启动的区别：快速恢复不把 cwnd 打回 1，Tahoe 会。
- SACK（选择确认）是补充：接收方在 ACK 里告诉发送方哪些段已经收到了，发送方只补真正丢的那几段，不用把一整个窗口都重发一遍。多个段丢在一个窗口时，NewReno + SACK 比老 Reno 更稳。
- 拥塞窗口 cwnd 是发送方自己控制的，和接收窗口 rwnd（对端通告的）是两回事，有效窗口 = min(cwnd, rwnd)。

## 实验 / 例子

场景：发送方发了段 1、2、3、4、5，段 2 在路上丢了。

1. 接收方收到 1，回 ACK 2（期待 2）。
2. 收到 3，发现 2 没来，回重复 ACK 2。
3. 收到 4，回重复 ACK 2。
4. 收到 5，回重复 ACK 2。
5. 发送方数到第 3 个重复 ACK，立即重传段 2，不等超时；同时 ssthresh = cwnd / 2，进入快速恢复。
6. 接收方收到重传的 2，接着把 3、4、5 一起确认，回 ACK 6。

排障时在 Wireshark 里看到的现象：连续的 Duplicate ACK + 一条 Retransmission，中间没有长时间的空等，就是快速重传在工作。如果看到大量 Retransmission 且间隔接近 RTO，说明丢包严重或对端根本没回 ACK，要查链路、缓冲区、MTU。

## 排障思路

- 应用卡顿先看 TCP 重传：是少量快速重传（偶发丢包，正常）还是大量超时重传（链路、拥塞、设备丢包）。
- 重复 ACK 很多但没有重传：可能是接收方乱序、或发送方实现没开快速重传，先确认两端 TCP 参数。
- 数据中心里常见诱因：Incast（多对一突发）、交换机缓存满、链路利用率长期接近 100%。这时调大缓冲只能缓一时，根因在流量模型。
- 别把重传都当成网络问题：接收方处理不过来、应用不读数据，也会表现为 rwnd 变小、发送方停顿，那是接收端问题，不是丢包。
